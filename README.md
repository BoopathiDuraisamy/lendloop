# LendLoop

> Borrow what you need. Lend what you don't.

A neighborhood tool-lending board. Neighbors list tools, request to borrow them for a date range, and approve, decline or close loans. n8n handles notifications and daily overdue reminders.

**Stack:** Next.js 16 (App Router) · TypeScript · Clerk (auth) · Convex (data + backend logic) · n8n (workflow automation, Docker) · Tailwind v4

---

## Features

| Area | What you get |
|---|---|
| Public page (`/`) | Tagline, read-only list of tools (**name + category only**), "Sign in to lend or borrow" (Clerk) |
| Browse (`/dashboard`) | All tools with availability (Available / On loan until… / booked ranges), category filter, request form with date range + note |
| My listings | Create, edit, delete your own tools (name, category, condition, description) |
| My requests | Your borrow requests, cancel while pending, overdue warning |
| Incoming requests | Approve / decline requests on your tools, mark loans returned, history |
| Admin | Remove any listing, view all loans (filter by status), toggle **Trusted Lender**, make/remove admins, see failed automation runs |
| Automation activity (bonus) | Each loan shows its recent automation events, e.g. "Notification sent via email, slack · 2 days ago" |

## Architecture

```
┌────────────┐  Clerk JWT   ┌──────────────────────────────────────────┐
│  Next.js   │─────────────▶│ Convex                                   │
│  (client)  │◀── realtime ─│  queries / mutations  ← RBAC helpers     │
└─────┬──────┘   queries    │  (convex/lib/auth.ts)                    │
      │ Clerk               │                                          │
      ▼                     │  mutation ─▶ automationEvents (outbox)   │
┌────────────┐              │          └▶ scheduler ─▶ n8n.ts action   │
│   Clerk    │              │                         │ HMAC-signed    │
└────────────┘              │  http.ts  (/n8n/*)  ◀───┼──── signed ────┼──┐
                            └─────────────────────────┼────────────────┘  │
                                                      ▼                   │
                            ┌──────────────────────────────────────────┐  │
                            │ n8n                                      │  │
                            │ 1. Request notifications (Webhook)       │──┤ write-back
                            │ 2. Daily overdue reminders (Schedule)    │──┤ fetch + write-back
                            │ 3. Error handler (Error Trigger)         │──┘ failure report
                            └──────────────────────────────────────────┘
```

**Frontend rendering.** Pages are client components that read data from Convex in real time, and sign-in state
is read in the browser (`useAuth`, Convex auth). Nothing on the server reads request cookies, so with Next.js 16
`cacheComponents` every route prerenders as a static shell and navigations are instant. The dashboard layout always
renders its page, and queries wait for the session via `useSessionQuery`. Authorization never depends on rendering:
it's enforced in Convex.

### Data model

- **users**: `tokenIdentifier` (from verified JWT), name, email, `role: admin|user`, `trustedLender`
- **tools**: `ownerId`, name, category, condition, description, `removedAt` (soft delete keeps loan history)
- **loans**: tool, owner, borrower, `startDate`/`endDate` (inclusive `YYYY-MM-DD`), `status: pending → approved | declined | cancelled → returned`, `reminderCount`, `lastReminderAt`
- **automationEvents**: `kind` (request_notification / overdue_reminder / workflow_error), `status` (pending / sent / failed / skipped), **unique `idempotencyKey`**, attempts, `channels` (per-channel result: `{email: {status, detail, at}, slack: …}`), and a human-readable `detail` built from them (e.g. "Notification sent via email, slack · discord failed: …")

### Loan rules (enforced server-side)
- You can't borrow your own tool. Dates must be valid, not in the past, and at most 30 days.
- Requests can't overlap an approved booking, and you get only one pending request per tool.
- Approving re-checks overlap and **auto-declines** conflicting pending requests (with notifications).
- Only the lender can mark a loan returned, because they're the one who can attest the tool is back.
- Owners can't delete a listing with an active or upcoming loan. Admin removal is allowed, and the loan stays returnable. Either way, pending requests are cancelled and the borrowers notified.

## Roles & access control

RBAC is enforced in Convex functions, not only in the UI:

- Every public function starts with `requireUser(ctx)` / `requireAdmin(ctx)` (`convex/lib/auth.ts`) and resolves the caller from the **verified Clerk JWT** (`ctx.auth.getUserIdentity()`). User ids are never accepted from the client for authorization.
- Ownership checks happen per operation. `tools.update` requires owner. `tools.remove` requires owner or admin. `loans.decide` and `loans.markReturned` require the lender. `loans.cancel` requires the borrower. `loans.listAll`, `users.listForAdmin`, `users.setTrustedLender`, `users.setAdmin` and `automation.recentFailures` require admin.
- **Admin is never self-assigned.** It comes from the `ADMIN_EMAILS` allow-list (verified email), an existing admin (**Admin → Members**), or the internal `users:setRole` (Convex CLI/dashboard only). See [Managing admins](#managing-admins).
- Functions n8n uses (`automation.*`) are **internal**. They can't be called from the browser, only through the signed HTTP endpoints.
- Errors are typed `ConvexError({code, message})` (UNAUTHENTICATED / FORBIDDEN / NOT_FOUND / BAD_REQUEST), and the UI shows the message.
- `src/proxy.ts` only redirects signed-out users away from `/dashboard`. It's a UX convenience, not a security boundary.

### Managing admins

**In the app (Admin → Members).** Admins see **Make admin** / **Remove admin** next to each member, with an inline
confirmation. `users.setAdmin` enforces the rules on the server:
- **You can't change your own admin role.** The acting admin always stays admin, so there's always at least one.
- **Allow-listed admins can't be removed in the app.** Members whose email is in `ADMIN_EMAILS` are labeled
  "admin · allow-list" and would be re-promoted on their next visit, so remove them from the list first.
- Non-admins calling `setAdmin` get `FORBIDDEN`.

**Bootstrap the first admin (and manage the allow-list)** from the [Convex dashboard](https://dashboard.convex.dev)
(your project → deployment) or the CLI:
- `ADMIN_EMAILS`, comma-separated: dashboard **Settings → Environment Variables**, or
  `npx convex env set ADMIN_EMAILS "you@example.com,other@example.com"`. The person becomes admin the next time they load
  the dashboard, provided Clerk reports that email as **verified** (Google and GitHub sign-ins always are). Removing an
  email from the list doesn't demote anyone; use Remove admin afterwards.
- `users:setRole` (internal, not callable from the app): dashboard **Functions → users → setRole** with
  `{"email": "x@example.com", "role": "admin"}` (or `"user"`), or
  `npx convex run users:setRole '{"email":"x@example.com","role":"admin"}'`. Useful for recovery, e.g. if no admin can sign in.

Avoid editing the `role` field directly in **Data → users**, because it bypasses these checks.

## n8n integration

### Wire format (both directions)

```
POST  body:     {"payload": "<JSON string>"}
      headers:  X-LendLoop-Timestamp: <unix seconds>
                X-LendLoop-Signature: sha256=<hex HMAC-SHA256(secret, "<timestamp>.<payload>")>
```

The signature covers the exact payload **string**, so neither side has to re-serialize JSON identically. The receiver rejects signatures older than 5 minutes (replay window) and compares in constant time. Invalid calls get a generic `401`.

### Workflow 1 – Request notifications (`n8n/workflows/request-notifications.json`)

1. A Convex mutation (request / approve / decline / cancel / return) writes an `automationEvents` row (key `notify:<loanId>:<event>`) **in the same transaction** and schedules `n8n.deliverRequestEvent`. This is a transactional outbox: no status change without its notification, and no notification for a rolled-back change.
2. The action builds a **minimal payload**: recipient name and email, tool name, dates, status, a link. Other users' ids, notes and descriptions are left out. It signs and POSTs to the n8n webhook, retrying with exponential backoff (5s → 40s, 5 attempts) on network errors, 5xx and 429. A permanent failure is recorded as `failed`, shown on the loan, and listed in Admin.
3. In n8n: **Webhook → Verify signature** (HMAC, timestamp; de-dupes by `eventId` using workflow static data) **→ 202 response → Plan deliveries (one item per channel) → email / Slack DM / Discord feed / mock → Sign → POST `/n8n/notification-status`** (retries 4×).
   Invalid signatures get a 401 and the run is marked failed (*Stop and Error*), so the error workflow reports it.

### Workflow 2 – Daily overdue reminders (`n8n/workflows/overdue-reminders.json`)

**Schedule (09:00) → Sign → POST `/n8n/overdue-loans` → split → Plan deliveries (email / Slack DM / mock, never Discord) → Sign → POST `/n8n/reminder-status`**

- Convex returns only approved loans past `endDate` that have **not already been reminded today**, each with a `reminderKey = overdue:<loanId>:<YYYY-MM-DD>`.
- The write-back is **idempotent on `reminderKey`**. A retried or re-run write-back returns `{duplicate: true}` and does not create a second row or increment `reminderCount`. A `failed` reminder can later be upgraded to `sent`.
- A failed send is written back as `failed` (visible on the loan) and retried on the next run.

### Workflow 3 – Error handler (`n8n/workflows/error-handler.json`)

Both workflows set `settings.errorWorkflow` to it (it must be published as well). An **Error Trigger** catches any failed execution (for example, HTTP retries exhausted or a rejected signature), logs it, and posts a signed report to `/n8n/workflow-error`, which is idempotent on execution id. Failures then show up under **Admin → Automation failures**. Nothing fails silently: Convex-side failures are recorded too, and n8n keeps all failed executions (`saveDataErrorExecution: all`).

### Secrets

- Convex: `N8N_WEBHOOK_SECRET`, `N8N_REQUEST_WEBHOOK_URL` via `npx convex env set`
- n8n: `LENDLOOP_HMAC_SECRET`, `LENDLOOP_CONVEX_SITE_URL` in `n8n/.env` (git-ignored), read via `$env` at runtime
- n8n channel secrets (SMTP, Slack, Discord): encrypted n8n credentials, created from git-ignored `n8n/secrets.env` (see [Notification channels](#notification-channels))
- The exported workflow JSON contains **no secrets and no deployment URLs**: only `$env.*` references, credential ids, and public API endpoints (Slack). Check with `grep -iE "secret|xoxb|password" n8n/workflows/*.json`.

## Local setup

### Prerequisites
- **Node 22+.** The Convex CLI refuses older versions: `npx convex …` and `npm run tunnel:refresh` fail with
  "Your Node version … is too old". With fnm: `fnm install 24` then `fnm use 24`, or prefix commands with `fnm exec --using=24`.
- Docker Desktop (for n8n)
- Free accounts: [Clerk](https://dashboard.clerk.com) and [Convex](https://www.convex.dev)

### 0. Decide where Convex runs

n8n runs on your machine in Docker. The two directions need different addresses depending on where Convex runs:

| | **Convex cloud** (default `npx convex dev`) | **Local Convex** (`npx convex dev --local`) |
|---|---|---|
| Convex → n8n: `N8N_REQUEST_WEBHOOK_URL` (Convex env) | public tunnel URL, set by `npm run tunnel:refresh` (step 6) | `http://localhost:5678/webhook/lendloop-request-events` |
| n8n → Convex: `LENDLOOP_CONVEX_SITE_URL` (`n8n/.env`) | `https://<deployment>.convex.site` (`NEXT_PUBLIC_CONVEX_SITE_URL` in `.env.local`) | `http://host.docker.internal:3211` |

Cloud is closer to production and is what this repo was tested with. Local needs no tunnel.

### 1. Install
```bash
npm install
```

### 2. Generate the shared HMAC secret
One value, used by both Convex and n8n. This works on any OS:
```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```
Copy the output. You'll paste it as `N8N_WEBHOOK_SECRET` (step 4) and `LENDLOOP_HMAC_SECRET` (step 6).
Run it again for a separate `N8N_ENCRYPTION_KEY` (step 6).

### 3. Clerk
1. Create an application at https://dashboard.clerk.com (enable Google, GitHub or email sign-in as you like).
2. **Integrations → Convex → Activate** (or create a JWT template named `convex`). No custom claims are needed: the
   token only carries the user id, and Convex fetches the name and verified email from Clerk's Backend API
   (`convex/clerk.ts`).
3. Note the **Frontend API URL** (`https://xxx.clerk.accounts.dev`) and the API keys.

### 4. Convex
```bash
npx convex dev            # log in, create/select a project; writes NEXT_PUBLIC_CONVEX_URL to .env.local
```
The first push stops with "CLERK_JWT_ISSUER_DOMAIN … not set". That's expected. In a second terminal:
```bash
npx convex env set CLERK_JWT_ISSUER_DOMAIN https://xxx.clerk.accounts.dev
npx convex env set CLERK_SECRET_KEY sk_test_...           # same key as .env.local
npx convex env set ADMIN_EMAILS you@example.com            # comma-separated; must be a verified email
npx convex env set N8N_WEBHOOK_SECRET <secret from step 2>
npx convex env set APP_URL http://localhost:3000
```
`npx convex dev` picks up the change and finishes the push. Keep it running.
`N8N_REQUEST_WEBHOOK_URL` is set in step 6. Until then, notifications are recorded as `skipped` and the app works normally.

Add to `.env.local` (see `.env.example`):
```
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...
```

### 6. n8n
```bash
cp n8n/.env.example n8n/.env
#   N8N_ENCRYPTION_KEY       = a second generated value
#   LENDLOOP_HMAC_SECRET     = the secret from step 2
#   LENDLOOP_CONVEX_SITE_URL = see step 0 (cloud: https://<deployment>.convex.site)
#   LENDLOOP_NOTIFY_CHANNELS = mock   (start here; add email/slack/discord later)

docker compose run --rm n8n-import  # imports the 3 workflows (+ placeholder credentials)
docker compose up -d n8n            # editor at http://localhost:5678 (create the owner account on first visit)

# Publish (activate) all three. n8n 2.x only runs an error workflow if it is published too.
docker compose exec n8n n8n publish:workflow --id=lendloopNotify01
docker compose exec n8n n8n publish:workflow --id=lendloopRemind01
docker compose exec n8n n8n publish:workflow --id=lendloopErrors01
docker compose restart n8n
```
Re-running `n8n-import` unpublishes the workflows, so publish them again afterwards.

**Convex cloud only: expose the webhook (and nothing else).**
```bash
npm run tunnel:refresh    # starts webhook-proxy + Cloudflare quick tunnel, sets N8N_REQUEST_WEBHOOK_URL in Convex
```
This runs the compose `tunnel` profile: a Cloudflare quick tunnel (no account needed) in front of an nginx proxy that
forwards **only** `POST /webhook/lendloop-request-events`. The n8n editor and REST API are never reachable from the
internet; every other path returns 404. Don't point a tunnel at port 5678 directly, because that would publish the editor.
Quick-tunnel URLs change on restart and can expire, so run `npm run tunnel:refresh` again whenever notifications fail
with network errors.

**Local Convex only:** `npx convex env set N8N_REQUEST_WEBHOOK_URL http://localhost:5678/webhook/lendloop-request-events`.

<a id="notification-channels"></a>
**Notification channels.** Set `LENDLOOP_NOTIFY_CHANNELS` in `n8n/.env` (comma-separated), then `docker compose up -d n8n`:

| Channel | Who sees it | Content | Needs |
|---|---|---|---|
| `email` | the affected person | full message + link | SMTP login (e.g. Gmail App Password) |
| `slack` | the affected person, as a **private DM** found by their LendLoop email | full message + link | Slack app bot token (`chat:write`, `users:read`, `users:read.email`) |
| `discord` | everyone in one channel | **anonymized**: tool + dates only. Only new requests, loans and returns; no declines, cancellations or overdue reminders | channel webhook URL |
| `mock` | nobody: logged to the n8n container (`docker compose logs n8n \| grep "\[mock\]"`), emails masked | subject line | nothing (default) |

Secrets go in `n8n/secrets.env` (copy `n8n/secrets.env.example`, git-ignored), then run
`docker compose run --rm n8n-credentials`. It stores them as encrypted n8n credentials (**LendLoop SMTP**,
**LendLoop Slack bot**, **LendLoop Discord webhook**). `secrets.env` is only given to that one-shot container, so the
running n8n never has passwords or tokens in its environment, and workflow JSON references credentials by id only.

Each channel's result is written back separately and shown on the loan, e.g.
"Notification sent via email, slack · discord failed: …". Sends retry 3×. Some nodes (Discord) report failures as
normal output items, so the "Mark sent" step checks every item for an `error` before recording success.
Placeholder credentials (created by `n8n-import` for anything not configured) let the workflows publish, because n8n
won't publish a workflow that references a missing credential. Sends through a placeholder fail visibly.

## How to verify

**Signed endpoints, replay window, idempotency.** Works with any Node version and reads the secret from `n8n/.env` without printing it:
```bash
npm run verify:integration                 # unsigned/forged/stale → 401, signed → 200, loan/key mismatch → 404
npm run verify:integration -- --writeback  # + same reminder write-back twice → applied once, then {duplicate:true}
```
`--writeback` marks one overdue loan as reminded today without sending anything, so it's opt-in.

**Forged webhook into n8n** shows up as a failure in the app:
```bash
curl -i -X POST http://localhost:5678/webhook/lendloop-request-events -H "content-type: application/json" -H "x-lendloop-timestamp: 1" -H "x-lendloop-signature: sha256=forged" -d "{\"payload\":\"{}\"}"
```
Expect `401 {"error":"invalid signature"}`. A few seconds later **Admin → Automation failures** lists
"LendLoop – Request notifications › Flag rejected call: Rejected webhook call: stale timestamp".

**RBAC is enforced on the server**, not just hidden in the UI. Call an admin-only function as the demo user Bob
(Convex dev deployments let you set the caller's identity):
```bash
npx convex run --identity "{\"tokenIdentifier\":\"seed|bob\"}" loans:listAll "{}"                # → FORBIDDEN
npx convex run --identity "{\"tokenIdentifier\":\"seed|bob\"}" users:setTrustedLender "{\"userId\":\"<any user id>\",\"trusted\":true}"  # → FORBIDDEN
```

**End-to-end notification.** As a second user, request one of your tools. The loan's activity line shows
"Notification sent via …" within seconds, and the message arrives on each enabled channel (with `mock`:
`docker compose logs n8n | grep "\[mock\]"`).

**Overdue reminders.** After `seed:demo`, open *LendLoop – Daily overdue reminders* in n8n and click
**Execute workflow** (or `docker compose exec -e N8N_RUNNERS_BROKER_PORT=5690 n8n n8n execute --id=lendloopRemind01`).
Overdue loans show "Overdue reminder sent via …". Run it again: nothing is sent and `reminderCount` doesn't change.

## Security & data-minimization decisions

- **Public page shows name + category only.** `tools.listPublic` returns nothing else: no owner, description or availability.
- **Signed-in views show display names, never contact details.** Emails are visible only to admins and to the n8n notification payload for the single recipient.
- **n8n gets the minimum.** One recipient's name and email, the tool name, the dates and the status. No other user ids, notes or descriptions. The overdue feed is the same: borrower name and email, tool, due date.
- **Third parties see only what delivery needs.** SMTP gets the recipient's address and message. For Slack DMs, the recipient's email is sent to Slack's API (`users.lookupByEmail`) to find their account; nothing else is sent for people outside the workspace. Discord gets no personal data.
- **Per-channel minimization.** Email and Slack are private to the affected person. Discord is a shared channel, so it gets an anonymized feed (tool + dates, no names or emails) and never gets overdue reminders. Mock logs mask emails (`j***@example.com`).
- **Channel secrets** (SMTP password, Slack token, Discord webhook URL) live only in n8n's encrypted credential store: never in workflow JSON, git, or the running n8n's environment.
- **Identity comes from the verified JWT**, and the user row is keyed by `tokenIdentifier`. Name and email are fetched server-to-server from Clerk's Backend API (or taken from token claims if configured), never from client arguments. Admin requires an email in `ADMIN_EMAILS` that Clerk reports as **verified**.
- **HMAC both ways**, with timestamped replay protection, constant-time comparison, a generic 401, a 16 KB body cap and per-field validation on every inbound payload.
- **Idempotency everywhere it matters.** Outbound events are keyed `notify:<loan>:<event>`, and n8n also de-dupes by `eventId`. Reminders are keyed `overdue:<loan>:<date>` and errors `n8n-error:<executionId>`.
- **Soft deletes** keep loan history readable for both parties after a listing is removed.
- **Server-side validation** covers text lengths, enum categories and conditions, date formats and ranges, and overlap checks.

## What I'd change for production

- **Email at scale**: switch SMTP from Gmail to a transactional provider (Resend, SES, Postmark) with SPF/DKIM on your domain, and add per-user notification preferences and unsubscribe links.
- **Secrets**: use a secrets manager (Doppler, AWS SM or 1Password) for n8n env and Convex env, rotate the HMAC secret with a dual-key verification window, and use separate secrets per direction and per environment.
- **n8n hardening**: pin the image version, use Postgres instead of SQLite, run queue mode with workers, serve over HTTPS behind a reverse proxy, put SSO on the editor, and keep the webhook path unguessable and IP-allowlisted where possible.
- **Replay protection**: store seen nonces or eventIds server-side (not just a timestamp window), and sign responses too.
- **Ingress**: replace the Cloudflare quick tunnel with a named tunnel or HTTPS ingress on a stable domain, keeping the path allow-list.
- **Redelivery**: notifications that exhaust their retries during an outage stay `failed`. Add a scheduled sweep (or an admin "retry" button) that re-enqueues them once n8n is reachable.
- **Abuse limits**: rate-limit the public webhook at the proxy and de-duplicate rejected-call reports, so a flood of forged requests can't fill the Admin failures list.
- **Clerk webhooks** to sync users and deletions (`user.deleted` → anonymize), instead of lazily upserting on sign-in. Manage roles via Clerk metadata or organizations.
- **Scale**: paginate lists (`usePaginatedQuery`), denormalize availability onto `tools`, run the overdue query as a cursor or batched job, and rate-limit mutations (e.g. `@convex-dev/rate-limiter`).
- **Observability**: alert on the error workflow (Slack or PagerDuty), use a Convex log stream to Datadog or Axiom, and add a dead-letter view with a "retry" button for failed notifications.
- **Time zones**: store a neighborhood time zone and evaluate "overdue" in local time (currently UTC).
- **Tests and CI**: `convex-test` unit tests for RBAC and idempotency, Playwright for the main flows, and lint, typecheck and `n8n:build --check` in CI.
- **Privacy**: a data-retention policy for automation events and loan history, and a data export and delete flow.
